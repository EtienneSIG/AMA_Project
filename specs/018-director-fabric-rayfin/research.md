# Phase 0 Research — Director Portal Native Fabric (Rayfin) App

**Feature**: `018-director-fabric-rayfin` | **Date**: 2026-06-26

All open clarification items from the spec were resolved in the Clarifications session
(`spec.md` → ## Clarifications → Session 2026-06-26), now **confirmed by the user with sources**:
[Fabric Apps — Rayfin](https://www.microsoft.com/en-us/microsoft-fabric/features/rayfin) ·
[Create & deploy a Fabric app with the Rayfin CLI](https://learn.microsoft.com/fabric/apps/create-app-with-cli).
This document records the resulting decisions, rationale, and rejected alternatives.

---

## R1 — What "Rayfin" is

- **Decision**: **Rayfin is Microsoft's Fabric Apps framework/CLI (preview)** for building full-stack
  apps with **Microsoft Fabric as the backend**. The director analytics app is a **Rayfin Fabric App**:
  a Fabric-hosted backend/data model plus a static frontend, scaffolded and deployed with the Rayfin CLI.
- **Rationale**: This is the user's explicit, first-party choice. It keeps backend + compute inside
  Fabric (EU capacity), provides a supported build/deploy workflow, and natively replaces Power BI Embedded.
- **Key CLI workflow**:
  - Scaffold: `npm create @microsoft/rayfin@latest -- director-fabric-app --workspace <eu-workspace>` (or `npx rayfin init .`).
  - Local dev: `npm run dev` (runs frontend locally, deploys backend to Fabric).
  - Auth: `npx rayfin login` (401/403 → re-login).
  - Deploy: `npx rayfin up` (preview with `--dry-run`; status `npx rayfin up status --json`).
  - Partial deploy: `npx rayfin up db apply` (data-model only; `--force` for destructive) · `npx rayfin up staticapp deploy` (frontend only).
- **Alternatives considered**:
  - *Custom web module over the Fabric SQL analytics endpoint (TDS)*: an earlier autonomous assumption — **rejected**; not what "Rayfin" is.
  - *Microsoft Fabric Workload Development Kit (lower-level workload SDK)*: heavier than the Fabric Apps framework for this reporting app — rejected.
  - *Keep Power BI Embedded*: rejected per the request; retained only as a fallback.

## R2 — Project layout (generated by Rayfin)

- **Decision**: The Rayfin project (`demo/apps/director-fabric-app/`) contains:
  - `rayfin/rayfin.yml` — app services + deployment settings (target Fabric workspace/capacity).
  - `rayfin/.env` — CLI environment values (EU workspace; secrets not committed).
  - `rayfin/data/` — the **Fabric-hosted data model** (governed aggregate views + suppression logic).
  - `src/` (project root) — the static frontend from the chosen Rayfin template.
- **Rationale**: Matches the documented Rayfin project structure; keeps the app self-contained.

## R3 — Data source feeding the app

- **Decision**: The Rayfin app's Fabric backend reads the existing **EU-resident mirrored analytics**
  (`demo/ml/fabric_mirroring/`, sourced from `pg-learneu-demo`). The `rayfin/data/` model exposes only
  **governed, aggregated** views (class trends, establishment/national benchmarks) — no learner-level rows.
- **Rationale**: One source of truth; preserves the Feature 005 parity baseline; no new ETL or data classes.
- **Alternatives considered**: new Lakehouse/ETL (duplication — rejected); the app holding its own copy of raw data (rejected — would create a new learner-data store).

## R4 — Where suppression & row-level scope run (compliance-critical)

- **Decision**: **In the Rayfin Fabric backend** (data model + backend query layer), before any aggregate
  reaches the frontend. Reuse Feature 005's approved K-anonymity thresholds (class ≥ 10, establishment ≥ 30,
  national ≥ 100) + indirect re-identification rules, re-implemented Fabric-side. The director's authorised
  scope is bound in the backend (fail-closed); the frontend cannot widen scope or see pre-suppression data.
- **Rationale**: Because Rayfin moves the backend into Fabric, the compliance gate must move with it. The
  "no learner-level data leaves the backend" guarantee is preserved — it is now the Fabric-app backend, not
  director-portal helpers.
- **Alternatives considered**: suppression in the frontend (forbidden — exposes pre-suppression data);
  suppression only in director-portal after the app returns data (rejected — the app's backend is the
  authoritative gate and may be accessed directly).

## R5 — Authentication & identity

- **Decision**: Build/deploy via `npx rayfin login` (developer/service identity with Fabric workspace
  Contributor+). Runtime app access uses the Fabric Apps app identity within the EU workspace; the host
  director-portal continues to gate director sessions and pass authorised scope context to the embedded app.
- **Rationale**: Uses the framework's native auth; no secrets stored in the repo.

## R6 — Migration / coexistence with Power BI Embedded

- **Decision**: Deploy the Rayfin app, then switch the director portal's reporting surface via
  `config/reporting.json` (`backend: powerbi-embedded | fabric-app`) to embed/link the Rayfin app. Power BI
  Embedded stays as a fallback until validated parity; then retire its tokens/config.
- **Rationale**: Reversible, low-risk cut-over (SC-006); satisfies FR-007/FR-008.
- **Alternatives considered**: hard cut-over (higher risk, no rollback — rejected).

## R7 — Embedding the Rayfin app in the director portal

- **Decision**: The director portal embeds the Rayfin app frontend as an **iframe of the hosted Fabric app URL**
  (from `rayfin up status`), surfaced in `demo/apps/director-portal/public/index.html`, preserving the portal
  shell, director auth, navigation, and the `powerbi-embedded | fabric-app` switch.
- **Rationale**: Meets FR-006 (consistent portal UX) while the analytics + backend run on the Fabric App.
  An iframe of the hosted app is the simplest supported surface and keeps the app's full-stack model intact
  (the embedded frontend calls its **own** Fabric backend; the portal does not proxy report data).
- **Open follow-up**: confirm the Fabric item embed token/URL format and any required allow-listing for the iframe
  during `/speckit.tasks`.

## R9 — Audit & scope path (resolves analysis finding I1)

- **Decision**: Because the embedded app calls its **own** Fabric backend (R7), the authoritative compliance
  controls live **in the Rayfin Fabric backend**:
  - **Row-level scope**: the director portal mints a **signed scope context** (authenticated director identity +
    authorised `schoolIds/regionIds`, short-lived) and passes it to the embedded app at load; the Rayfin backend
    **verifies and enforces it fail-closed** on every query. The frontend cannot widen scope.
  - **Suppression**: enforced in the Rayfin backend (R4) before any aggregate reaches the frontend.
  - **Access audit (Art. 12)**: **written by the Rayfin backend** for every report access (director, scope, report,
    period, state, correlation id) and **ingested by the director portal into the shared `ReportingAccessLog`**
    (`demo/apps/_shared/db`) so compliance reviewers see one unified audit trail.
- **Rationale**: Keeps "Fabric as backend" intact (no portal proxy of report data) while preserving a single,
  portal-visible audit trail and fail-closed scope. The portal remains the session/auth + backend-switch authority.
- **Contract impact**: `GET /api/reporting/report/:id` is served by the **Rayfin app backend** (not a portal route);
  the **portal** retains `/api/reporting/metadata`, `/api/reporting/health`, and `/api/reporting/embed/:id` (PBI fallback),
  plus an **audit-ingest** path. The signed scope context is issued by the portal at embed time.
- **Alternatives considered**: *portal proxies all report data* (centralises audit but defeats Fabric-as-backend and
  duplicates the data path) — rejected; *no portal-visible audit* (app-only logs) — rejected (compliance needs one trail).

## R8 — Fabric Apps is in PREVIEW (risk)

- **Decision**: Treat the **Fabric Apps (Rayfin) preview** as a tracked delivery risk, not a blocker.
  Require the workload to be enabled in the tenant; gate cut-over on validated parity; keep Power BI
  Embedded as the reversible fallback; re-verify behaviour against Rayfin CLI updates.
- **Rationale**: Preview features can change; the fallback + parity gate contain the risk.
